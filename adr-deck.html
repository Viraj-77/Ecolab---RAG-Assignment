The Scenario

Tech Radar Concierge — read meets write.

A user asks about the radar; sometimes they want to understand it, sometimes they want to change it. The orchestrator decides which agent to send them to.

A

RAG Agent · Reads

Answers natural-language questions about the radar's history and rationale, grounded in the corpus from Exercise A.

answer-from-corpus

B

MCP Agent · Writes

Mutates the radar — adds, moves, retires technologies — through the Variant 2 MCP proxy from Exercise B.

propose-radar-change

C

Orchestrator · Routes

Classifies intent, queries the registry by capability, dispatches an envelope, and persists the workflow row.

POST /request

Why three? Each agent does something the others cannot. Collapse them into one and you lose the read/write seam, the registry contract, and the ability to swap any single piece.

System Architecture

Capability-routed, not URL-coupled.

The orchestrator never knows where an agent lives — it asks the registry by capability at every dispatch.

Architectural Decision
ADR-001Accepted

We picked one boss, not a swarm.

In one line
One orchestrator runs the show. It knows what step is next, what failed, and what to retry.
Why
With three agents, the hardest thing is finding out what went wrong. Choreography (agents shouting events at each other) makes that harder, not easier.
What we gave up
If the orchestrator dies, the system pauses. We accepted that — its state is in SQLite, so a restart picks up where it left off.
Revisit if
The team or the agent count doubles. Then we'll think about an event broker.
What we care aboutOrchestrationChoreography
Easy for a new engineerYes — one entry pointNo — events everywhere

Architectural Decision
ADR-002Accepted

Plain HTTP. Boring on purpose.

In one line
All four services talk over HTTP + JSON. You can debug it with curl.
Why
Every Python developer already knows it. No proto files, no broker UI, no infra to spin up.
Rejected
gRPC — too much schema work for a 3-agent toy. NATS / Redis — broker overhead unjustified at this size.
Architectural Decision
ADR-003Accepted

One envelope. Used everywhere.

In one line
A single Pydantic Envelope class. Same type on the wire, in the agent, in the test.
Why it matters
If we used different shapes in different places, we'd waste hours hunting "why is this field missing?" bugs.
correlation_idSame across every message in one user request — stitches a workflow's logs together.
causation_idThe id of the message that caused this one — reconstructs the call chain.
idempotency_keyReceiver dedupes on this. A retried envelope reuses the same key.
message_idUnique id for THIS envelope — distinct from the idempotency key.
senderLogical name of the agent emitting this envelope (matches its registry name).
recipientLogical name of the intended receiving agent or capability.
capabilityWhat is being invoked — e.g. answer-from-corpus.
payloadThe actual request/response body — schema is per-capability.
timestampISO-8601 UTC instant — used for timeline ordering in traces.
Architectural Decision
ADR-004Accepted

Find agents by what they do, not where they live.

In one line
The orchestrator never hardcodes URLs. It asks the registry for whoever offers a capability.
How agents stay alive
Agents heartbeat every 10 seconds. If a heartbeat doesn't come in 30 seconds, the registry forgets them.
Why
If an agent moves to a new port (or you swap a 4B model for an 8B one), nothing else has to change.
Architectural Decision
ADR-005Accepted

Fail loudly. Never silently.

In one line
5-second timeout → retry up to 2 more times with the same idempotency key → if still failing, write a row to the poison table.
Why same key
If the receiver did the work but its reply was lost, the retry doesn't do it twice. The agent recognises the key and returns the cached answer.
If the orchestrator crashes
Workflow rows are in SQLite. On restart, anything stuck in in_progress can be picked up — no work is lost.

Architectural Decision
ADR-006Accepted

One log file. One ID. Thirty seconds.

In one line
Every event lands as one JSON line in observability/logs.ndjson. Filter by correlation_id and you have the whole story.
The "why did X call Y" answer
The classifier writes a line that says: chosen capability, reason, and (when an LLM picked it) the full prompt. So "why" is one row, not a re-run.
How to use it
python -m observability.query <correlation_id> prints the timeline.
Things That Bit Us

Honest list — what tripped three interns up.

Some of these are embarrassing. We're listing them anyway, because the next person on this codebase will hit the same things.

"Address already in use" 😩silly

We Ctrl-C'd uvicorn during a demo. Zombie process kept :8002. Spent ten minutes "debugging" before realising.

Fix: wrote scripts/check-ports.sh + free-ports.sh. make up now refuses to start if a port is taken.

Wrong folder, wrong everything 📁silly

Ran make up from the parent directory. Got "no rule to make target". Stared at it for a minute.

Fix: README opens with the exact cd command. Lesson: always assume the next person is in the wrong folder.

"command not found: python" 🐍silly

macOS only ships python3. Forgot to source .venv/bin/activate before running tests.

Fix: README spells out .venv/bin/python -m … as the safe path that works regardless of activation.

The radar said "already exists" 🤷silly

The e2e test wrote gemma3-orchestrator-e2e to the radar. Second run: rejected. Panicked. The test was actually passing — we just didn't read it.

Fix: document rm -f exercise-b-mcp/mcp-server/radar_working.json as the demo-reset step.

The envelope drifted in two places 🪤real

Early on, the orchestrator built an envelope dict by hand, while agents used the Pydantic class. One field rename later, things broke at runtime — no type-check caught it.

Fix: imported the same Envelope class everywhere. Killed the dict version with extreme prejudice.

Retries without idempotency ♻️real

First retry implementation generated a fresh idempotency key on each attempt. The MCP agent happily added the same technology three times.

Fix: the retry path reuses the original envelope. Verified by the chaos test — three attempts, one key.

SIGTERM and SIGKILL behave differently 💀real

We expected both to look the same. SIGTERM (graceful) deregisters → orchestrator fast-fails. SIGKILL (sudden) leaves the registry pointing at a corpse → retries → poison.

Fix: documented both paths in failure-modes.md. The chaos test exercises both on purpose.

Forgetting to git pull first 🌿silly

One of us pushed Person 2's agent file before pulling Person 1's envelope changes. Merge conflict took longer than the actual code.

Fix: PLAN.md has a "before every work session, run this" block. We follow it now.

ndjson logs grew fast 📈real

Every chaos test added another correlation_id worth of rows. After a dozen runs, the file was 2MB and --tail was slow.

Fix: the query tool reads ts-sorted on a single correlation_id, so size doesn't matter for "why did X call Y". File rotation is a future-us problem.

The RAG agent had no real backend 📚real

Exercise A's agent wants Azure OpenAI keys + a ChromaDB index. On a fresh laptop without those, it would crash at startup.

Fix: the wrapper falls back to a clearly-labelled stub reply. The A2A plumbing stays runnable; the message says "[rag-agent stub]" so no one is fooled.
Common Smells — Avoided

Six smells the spec calls out. Six checks.

  • No registry. Capabilities are queried, not URLs. GET /agents?capability=… at every dispatch.
  • "Idempotency? It worked once." Chaos test fires three retries; all three reuse the same idempotency_key.
  • Untraceable orchestrator decisions. intent_classified events carry the chosen capability + reasoning + (when LLM) the prompt.
  • Three agents that all do the same thing. Read vs write split — each agent has a job no other agent can do.
  • Orchestrator with no persisted state. SQLite workflows table; rows survive a process restart.
  • Envelope only on the wire. The Pydantic Envelope is the type used in agents and orchestrator alike — not a wire-only struct.
